# PRD → 线框图生成器

> JD 里 **PRD 撰写 54%、原型设计 35%**——但真实工作里这两件事是连着的：
> 写完 PRD 还要手工画一版线框给开发看，而且经常**文档改了图没改**。
>
> 这个工具做的事：读 PRD，自动生成线框图。让文档和原型**从同一份源同步**。

---

## 为什么做这个

三个真实痛点：

1. **重复劳动**：PRD 里已经写清了有哪些模块、每个模块干什么，画图等于抄一遍
2. **不一致**：PRD 改了第 3 版，线框图还是第 1 版，开发按图做，白做
3. **工具门槛**：Figma 学两周才能画出像样的图，但我需要的只是"和开发对齐有几个模块"

所以定位很克制：**只出线框，不出高保真，不做交互。**

---

## 运行

```bash
python prd2wire.py examples/prd-matcher.md
# → examples/prd-matcher.wire.html
```

浏览器直接打开即可，单文件、无依赖。

---

## 它怎么工作的

**输入**：一份结构化的 PRD（markdown）

**解析规则**（关键设计决定：用规则不用大模型）：
- `# 一级标题` → 产品名
- `## 二级标题` → 功能模块（自动跳过"背景/目标/验收"这类非模块章节）
- 每个模块下的列表项 → 功能点（最多取 4 条，多了线框图会糊）
- 含"失败/超时/为空/无结果/非法/不支持"的条目 → 单独标记为**异常态**

**输出**：单文件 HTML，左侧模块导航 + 主区域卡片，异常态用黄色条单独标注。

---

## 为什么用规则不用大模型（这是最重要的取舍）

第一直觉是"让 GPT 读 PRD 生成原型"，但我算了一笔账：

| 方案 | 成本 | 稳定性 | 可解释性 |
|---|---|---|---|
| 大模型 | 每次调用要钱要等 | 同样输入可能出不同结果 | 出错不知道错在哪 |
| 正则规则 | 0 | 完全可复现 | 哪条规则没匹配上一眼看得出 |

PRD 的结构本身就相对固定（用标题分模块、用列表写功能点），**规则已经够用了**。
把大模型用在这里是"为了显得高级"。真正需要模型的地方是"这段 PRD 写得清不清楚"，不是"有哪些模块"。

> 这条判断在面试里很加分：**不是所有环节都该上模型。**

---

## 我踩的坑

**坑 1：第一版把所有列表项都算成功能点**
结果"异常与边界"章节里的 4 条异常全部变成功能卡片，线框图里出现了"提示信息不足"这种按钮。看着很蠢。

改法：给异常关键词单独建一张表，命中的移出功能列表，单独渲染成黄色警示条。

**坑 2：模块名带序号**
`## 三、核心流程` 原样输出成"三、核心流程"，导航栏里五个"一二三四五"。改法：正则剥掉中文序号前缀。

**坑 3：一开始想读 .docx 的 PRD**
后来发现产品团队写 PRD 用飞书/Notion，导出 markdown 最干净。**先支持 markdown，别一上来兼容所有格式**——这是典型的"想太多做不完"。

---

## 已知局限

- 只支持 markdown 格式 PRD
- 一个模块最多渲染 4 个功能点，超出部分丢弃（线框图本来就不该塞满）
- 不做布局算法，所有模块统一单列纵向排列
- 不支持图片/流程图占位

| JD 要求 | 怎么证明 |
|---|---|
| 需求分析与拆解 | PRD 的"不做什么"章节、异常分支、验收指标 |
| PRD 撰写 | `examples/prd-matcher.md` 是完整可读的 PRD |
| 原型设计 | 自动生成的线框图（虽不是 Figma，但证明理解信息层级） |
