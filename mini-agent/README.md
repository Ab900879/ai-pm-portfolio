# Mini Agent：用 100 行手写一个会调用工具的 Agent

> JD 里 **"AI Agent / 智能体原理与搭建" 37.8%**，面试几乎必问：
> **"Agent 和普通聊天机器人有什么区别？"**
>
> 这个仓库就是为了让你能**当场回答这个问题，并且敢让人追问细节**。

---

## 一句话答案

**普通聊天机器人只有一张嘴，Agent 多了一双手。**

嘴 = 会说；手 = 能决定"这件事该调用哪个工具"，然后读取工具返回的真实结果，再继续想。

---

## 跑起来

```bash
pip install openai
setx DEEPSEEK_API_KEY "sk-xxx"
python agent.py
```

真实运行输出：

```
问：现在几点了？
[step 1] 调用工具 get_time({})
[step 1] 观察结果：2026-10-19 11:33:17 星期1
[step 2] 直接回答
答：现在是 2026 年 10 月 19 日（星期一）11:33:17。

问：帮我算一下 (365-40)*24 是多少
[step 1] 调用工具 calculate({'expr': '(365-40)*24'})
[step 1] 观察结果：7800
[step 2] 直接回答
答：(365-40)*24 = 7800
```

**注意第 2 步：模型不是自己算的，是工具算的。** 这是 Agent 和聊天机器人最本质的差别——
聊天机器人会"猜"7800，Agent 是"拿到"7800。

---

## 核心循环（面试要能画出来）

```
用户提问
   ↓
[思考 Reason] 这件事我自己会不会？不会 → 该用哪个工具？
   ↓
[行动 Act]  输出 {"tool": "calculate", "args": {"expr": "..."}}
   ↓
[观察 Observe] 代码执行工具，拿到 "7800"
   ↓
[再思考] 有了 7800，可以回答了
   ↓
输出答案
```

这就是 ReAct（Reason + Act）。循环最多 3 次，防止死循环烧钱。

---

## 三个工具

| 工具 | 用途 | 为什么要工具 |
|---|---|---|
| `get_time` | 返回当前时间 | **模型不知道今天几号**，它的知识有截止日期 |
| `calculate` | 四则运算 | **模型算数是猜的**，三位数以上就容易错 |
| `search_kb` | 检索内部知识库 | **模型不知道你们公司的事**，这就是 RAG |

这三个工具正好对应模型的三类硬伤：**不知道现在、不会算准、不知道内部信息**。
理解了这张表，你就理解了为什么需要 Agent。

## 代码里最关键的 3 行

```python
messages.append({"role": "assistant", "content": msg})          # 记下模型决定调用工具
messages.append({"role": "user", "content": f"工具返回：{observation}..."})  # 把结果喂回去
```

**这两行就是"Agent"全部的秘密。** 把工具结果当成一条用户消息塞回对话，
模型就能基于真实结果继续推理。没有这一步，它就只是个会说话的机器人。

## 我踩的坑

**坑 1：一开始让模型输出自然语言说"我要调用计算器"**
解析起来极其脆弱，模型有 20 种说法。改成**强制输出一行 JSON**，成功率从 60% 提到接近 100%。
> 这条经验可以直接迁移到任何需要模型输出结构化内容的场景。

**坑 2：工具的"描述"写得太随便**
最初写的是 `"calculate": "计算"`，模型经常拿它去算日期差。改成
`"计算数学表达式，参数 expr 是四则运算字符串，如 3*7+2"` 之后才稳定。
> **Agent 的效果，一半取决于工具描述写得好不好。** 这是产品经理该干的活，不是算法。

**坑 3：没设最大步数**
有一次模型反复调用搜索，转了 7 圈才停。加了 `max_steps=3` 之后，费用可控了。
> 产品经理要关心的是"一次对话最多花多少钱"，这跟技术无关，是产品决策。

## 已知局限

- 工具调用的解析靠正则，模型输出格式跑偏时会失效（生产环境应该用 Function Calling 原生接口）
- 没有记忆，多轮对话不保留上下文
- 没有并行调用（真实 Agent 经常一次调多个工具）
- `calculate` 用 eval，虽然有正则白名单，生产环境应该用 AST 解析

---

## Roadmap

- [ ] 换成原生 Function Calling（tool_calls 字段），不再靠正则解析
- [ ] 加多轮记忆（Buffer + Summary）
- [ ] 加"工具调用日志"，能统计每个工具的调用次数与失败率（这是 Agent 运营的核心指标）
- [ ] 做成 Coze 工作流版本，让非技术同学也能用

## 面试怎么讲这个项目

**问：Agent 和聊天机器人的区别？**

> 「我用 100 行手写过一个最小 Agent。核心差别是它有一个循环：思考→调用工具→看结果→再思考。
> 比如问'现在几点'，普通模型会编一个时间，Agent 会调用 get_time 拿到真实时间再回答。
> 我做了三个工具，正好对应模型的三类硬伤：不知道现在、算数不准、不知道公司内部信息。
> 代码上最关键的就是把工具返回结果当成一条消息塞回对话，
> 这一步让模型从'猜'变成'基于事实说'。」

**追问：工具描述重要吗？**

> 「非常重要。我一开始把计算工具描述成'计算'，模型经常拿它算日期差。
> 改成'计算数学表达式，参数是四则运算字符串'之后就稳了。
> 所以 Agent 的效果一半在工具描述上，这活其实该产品经理干。」
