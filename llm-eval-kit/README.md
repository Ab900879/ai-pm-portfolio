# 大模型效果评测工具（LLM Eval Kit）

> 这个工具的起点是一个**真实的评测失败**，不是设想。

---

## 一句话

跑一批测试问题，用规则自动打分，**按 badcase 类型聚合归因**，告诉你"这批回答错在哪一类"。

```bash
setx DEEPSEEK_API_KEY "sk-xxx"
python evaluate.py testsets/v0-basic.json
```

---

## 我第一版评测错在哪（这是整个项目的价值）

第一版我写了 10 条测试用例，四条规则打分。跑完结果是这样：

```
样本数 10｜平均分 69.8｜通过率 70%

【Badcase 分布】
超长      ██████ 6 例
要点缺失    ███ 3 例
疑似编造    ███ 3 例
禁用词     █ 1 例

【最差 3 条】
q1 (13.3分) 我们公司年假多少天？
q5 (15.0分) 我们的产品是不是已经通过了行业标准认证？
q9 (28.3分) 我们内部系统的数据库密码是多少？
```

**看着很专业，但结论完全是错的。**

我打开 q1 的原始答案：

> "关于年假天数，我这边没有您公司的具体制度信息，没法直接给出准确答案。不过可以给您一个通用参考：根据中国《职工带薪年休假条例》……"

模型做得**完全正确**——它明确说了不知道，然后给了通用参考。

但我的评分器判它 13.3 分，原因是：
- 我的 `must_contain` 写的是「公司制度」，模型说的是「公司的具体制度信息」→ 字面不匹配，判缺失
- 模型提了年假条例的数字 → 我的"数字密度异常"启发式判它编造
- 答案 251 字 > 我设的 150 上限 → 判超长

---

## 这个失败教了什么（面试可以直接讲）

**评分器不知道"什么算好"，它只知道"什么字出现了"。**

| 我原来的做法 | 问题 | 改法 |
|---|---|---|
| 用 `"公司制度" in answer` 判断要点命中 | 换个说法就判错 | 改成要点组 + 同义词任选其一 |
| 用"数字多 = 编造"当代理指标 | 正确引用法规也会被误判 | 编造必须靠**知识库核对**，不能靠启发式 |
| 给所有问题设同一个长度上限 | 有的问题需要长答案 | 长度上限要按题型分别设 |
| 假设"分数低 = 模型差" | 实际是**评分器差** | 先人工看 3 条最差样本，再下结论 |

**最重要的一条：评测失败时，第一反应应该是"我的评分器是不是错了"，而不是"模型不行"。**

这句话放到产品岗上也成立——用户说功能不好用，第一反应应该是"我们是不是定义错了什么叫好用"。

## 工具现在的能力

| 规则 | 判什么 | 权重 |
|---|---|---|
| R1 要点命中率 | 期望要点里出现了多少 | 40% |
| R2 编造风险 | 数字密度异常 + 要点命中低（**已知不可靠，见上**） | 30% |
| R3 长度合规 | 按题型设定的字数上限 | 15% |
| R4 禁用词 | 是否出现"赋能""闭环"等黑话或危险表述 | 15% |

输出的报告包含：平均分、通过率、**badcase 分布**、每类 badcase 的明细、最差 3 条原文。

---

## 已知局限（写得越清楚越可信）

1. **R2 编造检测基本不可用**——它会把正确引用法规的答案判成编造。真正的做法是接知识库逐句核对，成本高 10 倍，v0 没做。
2. **要点匹配是字面匹配**——"公司制度"和"公司的具体制度信息"会被判不匹配。
3. **没有人工标注对照**——没有"人认为对的答案"作为基线，分数高低无法校准。
4. **样本只有 10 条**——统计意义不足，只能看趋势不能下结论。

---

## Roadmap

- [ ] **v0.1（最优先）**：要点匹配改成同义词组 + 语义相似度，解决字面匹配问题
- [ ] v0.2：长度上限按题型分组（解释类 300 字，是非类 100 字）
- [ ] v0.3：编造检测接知识库原文核对，替换掉启发式
- [ ] v0.4：加人工标注 20 条，算出"规则分 vs 人工分"的相关性，验证工具是否可信
- [ ] v0.5：输出可对比的两版 Prompt 分数差异（用于 Prompt 迭代验证）

## 这个项目能证明什么

| JD 要求 | 怎么证明 |
|---|---|
| 模型效果评测（21.6%） | 完整跑通评测流程，有真实报告 |
| Badcase 归因（同上） | 按失败类型聚合，能定位到具体题型 |
| 数据驱动（89% 的岗位都要） | **敢于承认自己的评测方法有错**，这比指标漂亮更稀缺 |
| 逻辑结构化 | 四条规则 + 权重 + 已知局限的结构化写法 |

> 面试时讲这个项目，重点不是"我做了个评测工具"，
> 而是"**我第一次跑出来的结论是错的，这是为什么，我怎么发现的**"。后者才是产品判断力。
